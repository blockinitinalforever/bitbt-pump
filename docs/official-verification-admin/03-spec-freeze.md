# Official Verification Admin — Frozen Spec

## Goal

Replace the website verification allowlist stored in frontend environment variables with identities managed from `admin.bitbt.com`.

## Requirements

### OVA-01 — Identity storage

The system stores an official identity with:

- channel type: `website`, `telegram`, `email`, `phone`, `linkedin`, or `x`
- display value entered by an administrator
- canonical normalized value used only for matching
- active/inactive status
- creation and update timestamps

`channel_type + normalized_value` must be unique. Channel values must satisfy platform-specific grammar after normalization.

**Acceptance**

- GIVEN an administrator submits `@BitBTVentures` as Telegram
- WHEN the record is saved
- THEN the original value is retained and the normalized value is `bitbtventures`

### OVA-02 — Authenticated administration

Authenticated administrators can list, create, edit, activate/deactivate, and delete official identities. All mutations use the existing session and Origin protections. Updates must include an explicit `is_active` value.

**Acceptance**

- GIVEN no valid admin session
- WHEN an admin identity endpoint is requested
- THEN the API returns `401`

- GIVEN a valid admin session
- WHEN a valid identity is created or updated
- THEN the normalized value is generated by the server and persisted

### OVA-03 — Public verification

The public API accepts `{ "type": "...", "value": "..." }`, normalizes the input with the same server-side rules, and returns the existing response contract:

- `{ "available": true, "official": true }` for an active match
- `{ "available": true, "official": false }` when the type exists but the value is not an active match, including malformed input
- `{ "available": false }` when the type has never been configured

**Acceptance**

- GIVEN active Telegram identity `@BitBTVentures`
- WHEN a visitor checks `https://t.me/BitBTVentures`
- THEN the response confirms it as official

- GIVEN the identity is inactive
- WHEN the same value is checked
- THEN the response is available but does not confirm it as official

### OVA-04 — Website compatibility

The existing website UI, channel types, translated messages, and result states remain unchanged. The browser posts to the same-origin Next.js route `/api/official-verification`, which:

1. rate-limits by visitor IP (Amplify edge headers)
2. rejects oversized bodies
3. proxies the lookup to the Rust API
4. fails closed when the upstream is unavailable

The Rust API remains available on `api.bitbt.com` for direct clients and defense in depth.

**Acceptance**

- GIVEN the backend API is available
- WHEN a visitor submits the existing verification form
- THEN the UI renders the existing official/unofficial/unavailable result

- GIVEN the backend cannot be reached
- WHEN a visitor submits the form
- THEN the route returns an error without treating the identity as official

### OVA-05 — Existing official identities

The migration seeds the currently published BitBT website, support email, Telegram, and X identities without overwriting future administrator changes.

## Security and operational constraints

- Public verification is rate-limited and body-limited at the website edge and again at the Rust API.
- Admin endpoints require the existing admin session.
- SQL uses bound parameters.
- Admin rendering uses text nodes, never HTML injection.
- The public Nginx host exposes only explicitly allowed API paths.
- No identity value is written to application logs.
